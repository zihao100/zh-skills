# git-commit-zh - 中文 Git 提交信息生成器

## 核心目标

分析当前工作区或暂存区的代码变更（`git diff` / `git diff --cached`），自动生成语义清晰、符合行业标准的结构化中文提交信息（Commit Message）。

## 触发场景

- 用户要求提交代码并编写提交信息（例如："帮我写个 commit"、"生成 commit message"）
- 用户完成了某项功能、修复或重构，准备进行 git commit
- 审查或整理历史提交记录使其规范化

---

## 提交信息结构规范

遵循 **Conventional Commits 1.0.0** 规范，采用中文描述：

```text
<类型>(<可选影响范围>): <简短中文描述>

[可选详细说明正文：详细说明变更背景、原因与实现逻辑]

[可选关联信息：如 破坏性改动说明、关联 Issue 编号]
```

### 1. 常用类型 (Type) 映射

| 类型 | 标签名 | 适用场景 | 示例 |
| :--- | :--- | :--- | :--- |
| **feat** | 新功能 | 引入新业务逻辑、新增接口或用户界面 | `feat(auth): 支持微信扫码登录` |
| **fix** | 修复缺陷 | 修复线上或测试环境中的缺陷、异常 | `fix(order): 解决并发扣减库存导致的负数问题` |
| **refactor**| 代码重构 | 代码结构调整，不改变外部行为也不修复Bug | `refactor(user): 提取权限鉴权中间件为独立模块` |
| **perf** | 性能优化 | 提高系统运行性能、减少内存消耗或加快查询 | `perf(query): 为用户订单表增加联合索引加速检索` |
| **style** | 代码格式 | 空格、分号、排版变动，不影响逻辑的调整 | `style(lint): 统一全仓 ESLint 代码风格` |
| **docs** | 文档更新 | 仅对 README、API 文档、注释等文档进行改动 | `docs(api): 更新支付网关回调接口参数说明` |
| **test** | 测试用例 | 增加或修改单元测试、集成测试、基准测试 | `test(cart): 增加购物车满减活动边界测试` |
| **chore** | 辅助变动 | 依赖升级、构建脚本、CI/CD 流程、辅助工具变动 | `chore(deps): 升级 Vite 版本至 5.2.0` |
| **revert** | 撤销提交 | 恢复此前的某次或某些 Commit | `revert: 撤销对短信服务超时时间调整的提交` |

## 工作流与操作步骤

### 第一步：检查变更内容
1. 检查是否存在已暂存的修改：`git status`、`git diff --cached`
2. 若暂存区为空，检查工作区修改：`git diff`
3. 归纳本次变更的核心目的，判断是否混合了多个独立功能（若改动过于庞杂，提示用户分拆多次 commit）。

### 第二步：确定类型与范围
- **Type**：根据上述映射表选取最精准的一个。
- **Scope**：精确反映受影响的模块或目录（如 `api`, `auth`, `payment`, `ui`）。

### 第三步：撰写描述
- **首行 Subject**：
  - 动词开头（如：支持、增加、优化、修复、重构、调整、移除）。
  - 控制在 50 个字符以内。
  - 末尾不加句号。
  - 中英文之间保持空格（例如：`fix(login): 修复 iOS 端 Token 刷新失败的问题`）。
- **正文 Body（复杂改动必选）**：
  - 说明改动的原因（Why）以及实现的方案（How）。
  - 如有重大改变（Breaking Change），单独标注。
- **注脚 Footer（可选）**：
  - 关联关闭 Issue，如 `Closes #123` 或 `Refs #456`。

## 交付格式示例

### 示例 1：常规功能交付（单行提交）
```text
feat(cart): 增加购物车批量删除与清空功能
```

### 示例 2：复杂缺陷修复（多行结构化提交）
```text
fix(payment): 解决极端高并发下微信支付重复回调问题

- 引入 Redis 分布式排他锁（超时时间 10s），防止同一订单同时进入处理流水
- 增加本地订单交易状态幂等校验逻辑
- 完善支付回调异常告警日志，增加流水号上下文追踪

Closes #204
```

### 示例 3：破坏性改动提交
```text
refactor(api)!: 重构用户个人中心接口为统一 REST 格式

BREAKING CHANGE:
原 GET /api/v1/get_user_info 已弃用，迁移为 GET /api/v2/users/{id}，返回字段中 user_name 重命名为 username。
```

## 质量自检清单

- [ ] 类型 (Type) 是否准确，无模糊乱用（如将重构写为 feat）
- [ ] 提交信息使用规范中文，避免口语化（如避免 "随便改了点东西"）
- [ ] 首行简练明了，聚焦核心意图
- [ ] 中英文、数字之间保留合理空格排版
